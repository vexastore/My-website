# Task — Restore portable dependency installation

## Summary

Repaired the storefront lockfile so clean npm installations work outside the
original Replit environment, restored local dependencies, and completed a
production build.

## Why

The lockfile contained tarball URLs for Replit's private package firewall. The
Fedora workspace could not resolve that internal host, leaving `node_modules`
incomplete and preventing `next build` from starting.

## How

Inventoried all lockfile URL hosts and found 166 Replit proxy entries. Replaced
only the common proxy prefix with the public npm registry prefix, leaving every
package name, version, integrity hash, dependency range, and lockfile structure
unchanged. Parsed the resulting JSON, ran a clean lockfile install, then ran the
production build and production dependency audit.

## When

Completed during the same 15 September 2026 session (Asia/Beirut), after the
admin architecture mapping.

## Where

- `package-lock.json`
- `CHANGELOG.md`
- `docs/index.md`
- `docs/04-development/dependencies.md`
- `docs/worklogs/2026/09/worklog-15-09-2026.md`

## Changes Made

- Rewrote 166 `resolved` tarball URLs from
  `http://package-firewall.replit.local/npm/` to
  `https://registry.npmjs.org/`.
- Restored 148 locked packages with `npm ci`.
- Added dependency installation and security follow-up documentation.
- Recorded the fix under the unreleased changelog.

## Problems Encountered

- The first clean install failed inside npm after repeated DNS failures against
  Replit's private proxy.
- npm's `replace-registry-host=always` option changed only the hostname and left
  the proxy-specific `/npm/` path, producing invalid public registry URLs.
- An unlocked fallback install stalled and was stopped.

## Solutions

- Repaired the exact lockfile URL prefix instead of relying on hostname-only
  replacement.
- Validated the JSON and used `npm ci` so package integrity hashes and locked
  versions were enforced.
- Kept the dependency audit findings separate from this registry portability
  fix so vulnerable package upgrades can be reviewed and regression-tested.

## Bugs Found

- Environment-specific package tarball URLs made the committed lockfile
  non-portable.
- The installed Next.js 15.5.23 is covered by a critical audit advisory whose
  patched range begins at 15.5.24.
- The production audit also reports vulnerable PostCSS, Sharp, and Undici chains,
  including the old `@vercel/blob` dependency chain.

## Bug Fixes

- Dependency installation portability is fixed by using public npm tarball URLs.
- Security advisories were identified and documented; package upgrades remain
  part of the agreed dependency-security remediation and were not silently
  bundled into this lockfile-source repair.

## Testing

- Unit Tests: no unit-test command exists in `package.json`.
- Integration Tests: `npm ci --no-audit --no-fund` passed and installed 148
  packages from the corrected lockfile.
- End-to-End Tests: no automated E2E command exists in `package.json`.
- Manual Testing: lockfile JSON parsing passed; URL inventory found zero Replit
  proxy references and 193 public npm registry references.
- Production Build: `npm run build` passed with Next.js 15.5.23, compiled
  successfully, and generated 160 of 160 static pages.
- Dependency Audit: `npm audit --omit=dev --json` completed and reported five
  production vulnerabilities: one critical, three high, and one moderate.
- Coverage summary: deterministic installation, lockfile integrity, compilation,
  static generation, and production dependency exposure were checked.
- Edge cases tested: scoped package tarball paths and proxy-specific `/npm/`
  paths were handled by the exact prefix rewrite.

## Performance Notes

No application runtime performance changed. The deterministic clean install
completed in approximately three minutes; the production compilation completed
in 6.7 seconds before page-data collection and static generation.

## Advanced Warnings

- The passing build skips type validation and linting according to the existing
  Next.js project configuration/output, so it is not evidence that type or lint
  checks pass.
- Critical/high dependency findings remain and should be upgraded before the
  production remediation is considered complete.
- `node_modules` is restored locally but remains disposable and untracked.
